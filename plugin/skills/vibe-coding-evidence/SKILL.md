# バイブコーディングの傾向を、外部データで裏づける

自分の案件の話だけだと一事例に聞こえる。外部の調査を添えると、聞き手自身の状況の話になる。

**このスキルを開いたら、まず `references/vibe-coding-evidence.md` を読む。**
そのうえで、資料に使う数値は Web 検索で最新版を確認してから載せる。

## 手順

1. `references/vibe-coding-evidence.md` を読み、使えそうな数値を選ぶ
2. 選んだ数値の出典を Web 検索し、**より新しい版が出ていないか確認する**
   （Veracode、GitClear、Stack Overflow、DORA、IPA、IBM は年次で更新される）
3. 一次に近い出典に当たって数値を確認する。まとめ記事の孫引きは使わない
4. 出典名と年月を、数値と同じページに置く。出典一覧のページには URL も併記する
5. 新しく見つけた数値は `references/vibe-coding-evidence.md` へ追記する

## 主張の組み立て

4つを順に置くと、経営層向けの論証になる。

1. **普及は前提** ── 使うかどうかの議論はもう終わっている
2. **動くことと安全は別** ── 生成コードの相当割合は動作確認では見つからない欠陥を含む
3. **機能を増やすほど確認の対象が増える** ── これは選択ではなく構造
4. **確認側は既に限界** ── だから確認の枠を先に決める必要がある

**3を落とすと「たまたま品質が悪かった案件の話」に聞こえる。**
トレードオフとして提示すると、聞き手が自分の状況に当てはめて聞く。


## 自分の事例と外部データは、切り替えを明示する

同じ資料に自分の監査結果と外部の統計を並べると、聞き手はどちらの話か分からなくなる。
**切り替わるページのリード文で明示する。**
「ここまでは一件の監査の話です。同じ傾向は、外部の調査にも表れています。」

## 事故事例は、何の例かを明示する

外部の事故を引くときは、**原因が公表されているものだけを使い、何の例として挙げているかを書く。**
AIの話をしている流れでランサムウェアの被害例を出すと、AI起因の事故だと誤読される。
「1位はランサムウェア。その1位の被害例として、2025年9月の◯◯社では……」のように、
どの項目の例なのかを文中で示す。対外資料では、ここを詰められると全体の信用が落ちる。

## やらないこと

- 出典不明の数字を使う（「8,000社が作り直している」のような、まとめ記事にしか出てこない値）
- 「外部調査では」で済ませる。調査主体の名前を本文に書く
- 前年の版の数値をそのまま使う。年が変わったら必ず確認する
- AIを全否定する立場で並べる。確認工程にもAIは使えるが、
  何を観点に置くかを決められる人が要る、という書き方にする

## 適用外

個別アプリのセキュリティ監査そのもの（`webapp-security-assessment` を使う）、
コードレビュー、AI 向けプロンプトのレビュー。
