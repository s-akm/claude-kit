# 自然な日本語ビジネス文書

## 前提

LLMの日本語は文法的には正しいが、語の選び方と文の組み立て方に癖が出る。読み手は理由を説明できないまま「なんか変」と感じる。以下はこれまでのプロジェクトで繰り返し指摘を受けた癖と、その直し方である。

顧客提出物では、**文体の自然さと同じくらい「約束の強さ」が問題になる**。断定してよいのは自社の意思決定であり、技術的な結果や相手の行動は断定できない。B章がそこを扱う。

置換表の全量は `references/phrase-table.md`、見出し・リード文・注記・表の構成ルールは `references/document-structure.md` にある。書き終えたら両方を通す。

## A. 文の組み立て

### A-1. 名詞化をやめて動詞で書く

LLMは動作を名詞に変えて「〜を実施します」「〜の対応が必要です」と書きたがる。

| AI的 | 自然 |
|---|---|
| 移行対象の選定を実施いただく | どこまで移すか決めていただく |
| 変換作業の実施が必要となります | 一件ずつ置き換える作業が要ります |
| ご確認をお願いいたします | ご確認ください |
| 費用への影響が発生します | 金額が変わります |

「〜の実施」「〜への対応」「〜の検討」「〜が発生」「〜につながる」は要注意。ほぼ常に動詞へ戻せる。

**「部分」「ところ」「形」「点」で文を終わらせない。** 名詞化のなかで一番出やすい。「詰める部分です」→「詰めます」、「対応していく形になります」→「順次進めます」。文末の名詞を消しても意味が通るなら、その名詞は不要である。

### A-2. 体言止めの連打をやめる

箇条書きで全項目を体言止めにすると、報告書ではなく単語帳になる。3項目以上が同じ形で並んだら疑う。文で書くか、体言止めにするなら短く切る。

### A-3. 対句・三点セットの反復をやめる

「A・B・C」の三点構成、「〜であり、〜であり、〜である」の対句は、LLMがリズムを作るために多用する。**並列は情報が増えるときだけ使う。** 並べた結果として読み手の理解が増えないなら片方を削る。「手順も確認の段取りも書き起こせません」は「作業の進め方が書けません」で足りる。

### A-4. 抽象名詞を具体に落とす

「観点」「軸」「側面」「要素」「事項」「箇所」は、たいてい中身が空。「費用面・期間面の観点から」→「金額と日数で見ると」。「判断軸をお示しします」→「ご判断の材料をお出しします」。

### A-5. 丁寧語を積み上げない

「〜させていただく」の連続、「〜いただければ幸いです」の多用は、丁寧というより自信のなさに見える。1文に敬語表現は1つで足りる。「ご検討いただけますようお願い申し上げます」→「ご検討ください」。

### A-6. 接続詞・つなぎ表現を削る

「また」「なお」「その上で」「つきましては」「加えて」は、無くても文がつながることが多い。消しても意味が通るなら消す。

### A-7. 誇張形容をやめる。効果を大きく言わない

「大幅に」「非常に」「極めて」「しっかりと」「確実に」は、根拠がないと空虚に響く。数字があるなら数字を書く。ないなら形容詞ごと削る。

あわせて、**「〜できます」「〜られます」と能力を語る形を、事実の記述に置き換える。**

| AI的 | 自然 |
|---|---|
| 基本設計書を起点にすると、画面に出る項目の一つずつまで対応させられます | 基本設計書を起点に、画面項目との対応を確認しています |
| 大幅にコストを削減できます | 作業量が半分程度になります |

「一つずつまで」のような程度の強調も落とす。

### A-8. 漢語を続けない

漢語が4つ以上連なると、目で追えても声に出すと詰まる。「8月中旬の仕様書確定に間に合わせる前提です」→「8月中旬までに仕様書を固めるには、この順番になります」。「〜化」「〜性」「〜的」「〜時」も密度を上げる。

これは4語以上の連続を戒めるものであって、和語の口語に逃げてよいという意味ではない。**述語を漢語にして、主語と目的語は平易に保つ**と、密度を上げずに文体だけ上げられる（C-2）。

### A-9. 並列する項目は文末の形を揃える

3つ並ぶうち1つだけ体言止め、1つだけ「です」止め、といった揺れが最も目立つ。**並列項目の末尾5文字だけを縦に並べて読む**と、揺れがすぐ見つかる。

### A-10. 前置きを重ねて主節を薄くしない

「〜という前提で」「〜を踏まえて」を積み、最後に中身のない動詞（整える／取り揃える／まとめる）で着地する型。「B案で進める前提で材料を整えました」→「移行方式はB案（区切って移す）を前提としています」。文の前半を全部消しても後半だけで用が足りるなら、前半は飾りである。

**資料の作り方を本文に書かない。** 「議事録から抜き出しました」「ヒアリングの結果をまとめました」は作業工程の説明であって、読み手が知りたい中身ではない。何が決まったかを書き、根拠は出典欄に置く。

### A-11. 他動詞を目的語なしで使わない

「組み立てます」「対応します」「進めます」「詰めます」を目的語なしに置くと、何をするのか読めない。目的語が思い浮かばないなら、その文はまだ内容が決まっていない。

### A-12. 何を指しているかを言い切る

説明を名詞で止めず、それが何を示すのかまで書く。

| AI的 | 自然 |
|---|---|
| 右の項番は各要件資料の番号です | 右の項番は各要件資料の記載箇所を示しています |

### A-13. 長い列挙は括弧に落とす

列挙を本文に流し込まず、括弧にまとめて文を短くする。

| AI的 | 自然 |
|---|---|
| 各資料への索引にあたります。機能一覧、API一覧、…データ定義の6本を指しています | 各資料への索引にあたります。（機能一覧、API一覧、…データ定義の6本） |

### A-14. 引用する文言は括弧で括る

画面に出る文言やメッセージを読点だけで区切ると、本文に紛れて読めない。「該当するデータがありません、と表示します」→「該当するデータがありません、というメッセージを表示します」。長さに応じて、括弧で括るか「というメッセージ」「というリンク」と受けを足すかを選ぶ。

## B. 約束の強さ

### B-1. 自社の意思は言い切る。技術的な結果は言い切らない

- **自社の意思決定・作業範囲**は言い切る。「〜する予定です」「〜と考えております」で濁さない。
- **技術的に保証できない結果**は言い切らない。旧URLの維持、表示の再現、外部サービスの挙動などは、実データを見るまで確定しない。「できるだけ」「おそれがあります」「同じ程度の」を使う。

| 断定してよい | 断定してはいけない |
|---|---|
| 移行ツールはこちらで作ります | 今までと同じURLで開ける状態を保ちます |
| 8月中旬までに計画書へ反映します | 記事を移すのとほとんど同じ手間がかかります |

方針として決まっていることでも、技術的な達成を約束したことにはならない。議事録に「URL構造を維持する」とあっても、実装面では「できるだけ」を残す。

### B-2. 相手にやってもらうことを断定形で書かない

自分の行為は「〜します」、相手の行為は「〜いただきたいと考えています」。「正確な件数を共有いただきます」→「正確な件数をご共有いただきたいと考えています」。期限を求めるときは日付を入れる（「8月7日までにご返送いただけますでしょうか」）。

### B-3. 言われていない懸念を否定形で先取りしない

「〜ではありません」「〜というわけではありません」は、相手がまだ言っていない不安を勝手に持ち出して否定する型。読み手はかえって「そう疑うべきなのか」と受け取る。**同じ内容を肯定文で書く。** 「記事を捨てる案ではありません」→「検索からの流入も保てます」。相手が実際にその懸念を口にした場合のみ、否定形で応じてよい。

### B-4. 決まったことを「案」と書かない

方向性が固まった項目を「〜する案です」「ご意向をうかがったうえで」と書くと、未決に見える。逆に、まだ決まっていないことを断定すると後で覆せない。**資料に載せる前に、一件ずつ決定済みか未決かを判別する。**

決定済みなら未決事項の一覧から外し、本文では言い切る。未決なら、どの資料のどこに未確定と書いてあるかを言えるものだけ残す。推測で「決まっていません」と書かない（`references/document-structure.md` の申し送り事項の節を参照）。

### B-5. 二択に見せない

前提が「どちらも必要」なのに「どちらにするか」と書くと、相手の判断を誤らせる。

| AI的 | 自然 |
|---|---|
| どちらの見せ方で全機能に広げるか、あわせてご相談させてください | 管理画面の機能はマニュアル、公開側の機能は基本設計書を起点にご確認いただけます |

### B-6. 相手の修正を根拠にしない

受け取った修正版で直っていない箇所を「了承された」と扱わない。相手は目についたものから直しているだけで、見落としもある。**違和感のある箇所は自分から挙げ、直し方の案を添えて確認する。**

## C. 語の統一

### C-1. 動詞の家族を先に決めて、資料全体で揃える

画面仕様で「出る」「出す」を使うと一気に口語になる。**すべて「表示する」「表示される」に寄せる。**

| 口語 | 資料の語 |
|---|---|
| アイコンが出ます | アイコンが表示されます |
| 記事の詳細が出なくなります | 記事の詳細が表示されなくなります |
| 選ぶ／押す | 選択する |
| 移動する／飛ぶ | 遷移する |
| 入れる | 入力する／挿入する |
| 引く（マスタから） | 取得する |
| 紐づける | 設定する |
| 並べる（資料の扱い） | 参照する |

曖昧語にも注意する。「項目ごと表示しません」は「項目ごとに」とも読めるので「項目自体を」と書く。全量は `references/phrase-table.md`。

### C-2. 口語を対外資料の語に置き換える

| 口語寄り | 対外資料 |
|---|---|
| マニュアルには載っていません | マニュアルには記載されていません |
| 現行にはありません | 現行には存在しない機能です |
| 実現はできますが | 実現可能ですが |
| 番号がありませんでした | 番号が付与されていませんでした |
| ご説明いたします | ご展開いたします |
| 申し送り | 申し送り事項 |
| いったん振った項番は動かしません | 採番済みの項番は変更しません |

ただし、区分の名称のように相手が繰り返し目にする短い語は平易なほうを選ぶ（「現行同等」ではなく「現行どおり」）。**読む人と語の長さで使い分ける。**

### C-3. 「同じ」ではなく「同等」

現行との比較は「同等」で書く。「同じ」は口語的で、細部まで完全に一致しているという誤解も招く。「入力内容と操作手順は現行と同等です」。

### C-4. 造語を使わない

社内で通じる短縮語を対外資料に持ち込まない。

| 造語・社内語 | 資料の語 |
|---|---|
| 実現先 | 記載箇所 |
| 洗い出し元 | 定義元 |
| 左軸 | （社内用語。対外資料では使わない） |
| 現行同等 | 現行どおり |
| 拾ってきたか | （口語。使わない） |

### C-5. 同じ対象を指す語を資料内で統一する

LLMは直前の文と語彙を変えたがる（同語反復を避ける癖）ため、抽象語に逃げやすい。「残すページ」と「対象」が同じものを指しているのに語が違う、という形で現れる。書き終えたら、同じものを何と呼んでいるか拾い出して揃える。

**成果物名・工程名は正式名称で書く。** 「仕様書」と「移行計画書」、「設計フェーズ」と「開発フェーズ」は別物として読まれる。手元の資料で正式名称を確認してから書く。

### C-6. 誰がやるかを書く。ただし自社を社名で呼ばない

責任範囲が読めない文は資料として使えない。一方で、自社が書いた資料のなかで自社を三人称の社名で呼ぶと、第三者が書いた報告書のように読める。**自社は「こちら」、または主語を省く。** 相手側は社名・敬称でよい。役割分担表のように列見出しで区別できる場合は、本文の主語を省ける。

### C-7. 指示語で中身を代替しない

「ここです」「この点です」「上記のとおり」は、指すものを名前で呼ばずに済ませる逃げ。資料は順番に読まれない前提なので、指示語は届かない。参照はページ番号だけを括弧で添える（「工数が大きく変わります（7ページ）」）。

### C-8. 文脈から自明な修飾語を毎回付けない

見出しで「新しいタグ分類」と示したら、本文以降は「タグ」で足りる。隣の文と重複する説明も削る。

### C-9. 読み手の語彙で書く

相手が広報担当ならシステム用語をそのまま出さない。ただし言い換えは「幼稚化」ではなく「翻訳」であること。相手は自分の業務のプロなので、business の側は正確に、technical の側だけ噛み砕く。

### C-10. 作業報告の過去形を、現在の状態に直す

「〜しました」は書き手の作業ログであって、資料が今どうなっているかを伝えない。「各資料の現在の項番を、そのまま使いました」→「各資料の現在の項番を使用しています」。

## D. 構成と記号

見出し、目次、リード文、注記、表の列構成、申し送り事項の判断基準は `references/document-structure.md` にまとめている。資料を組み立てる前と、書き終えた後の2回通す。

記号の扱いは以下。

- スラッシュでの並列（日／英、新規追加／既存編集）は「と」「、」に置き換える
- 矢印（→ ▶ ⇒）を装飾で足さない。既存の文言にあるものは消さない
- 段落の先頭に丸付き数字を置かない。資料名の一部なら「権限①シート」のように語を前に付ける
- 語の直後に付ける ※ の前は半角スペース（「変更あり ※」）。全角スペースを入れない
- **英字の略語・製品名の前後には空白を入れない**：`新しいCMSへ`／`静的なHTML`／`PDFは`
- **数字の前後には空白を入れる**：`4 ページ`／`556 件`／`2025 年 5 月`／`18 ％`。単位や助数詞は数字側に寄せる（`30〜50 人日`）

略語は語として読まれるので日本語と地続きでよいが、数字は視線を止めたい対象なので空白で分離する。1つの資料の中で混在させないことが最優先である。

## 手順

1. 内容を先に固める。何を言うかが決まる前に文体を磨かない
2. まず普通に書く
3. A章とC章で読み返し、該当箇所を書き換える
4. 並列項目の**末尾だけを縦に読んで**形の揺れを潰す（A-9）
5. 断定している文を拾い出し、自社の意思か技術的な結果かを判別する（B-1）。相手の行為を断定していないか確かめる（B-2）
6. 見出しだけを拾い読みして、単独で意味が通るか確かめる（`references/document-structure.md`）
7. 指示語（ここ・この点・上記）を検索して、指す対象に置き換える（C-7）
8. 同じ対象を指す語がぶれていないか拾い出して揃える（C-5）
9. 英数字まわりの空白を一括で見直す（D）
10. 「出ます／出します」「選びます」「押します」を検索して置き換える（C-1）
11. 過去形の文末を検索し、現在の状態の記述に直す（C-10）
12. 決定済みの項目を「案」と書いていないか確かめる（B-4）
13. **声に出して読む。** 息が続かない文、口に出して不自然な言い回しは直す。これが最も確実な検査である
14. 相手から修正版を受け取ったら、差分を機械比較して直し方の型を抽出し、同じ型を全文へ当てる（B-6）

### 納品前の機械走査

`scripts/scan_expressions.py` を実行する。Markdown・pptx・xlsx・docx からテキストを取り出し、置き換え済みのはずの表現が残っていないかを走査する。

```bash
python3 scripts/scan_expressions.py 提出予定のフォルダ
python3 scripts/scan_expressions.py deck.pptx --add "プロジェクト固有の語1" --add "プロジェクト固有の語2"
```

プロジェクトごとに指摘を受けた語は `--add` で足していき、最終的に `scripts/patterns.json` へ書き戻す。

## やらないこと

- 一文を長くしない（40〜60字で切る）
- 同じ語尾を3回続けない
- 「〜のではないでしょうか」で断定を避け続けない。自社の意思は言い切る
- 箇条書きに逃げない。理由や因果があるなら文で書く
- カタカナ語で誤魔化さない（「アジャイルに」「フェーズごとに」）
- 同語反復を避けようとして抽象語に逃げない。同じものは同じ語で呼ぶ
- 「書き起こす」「執り行う」など、場面の合わない硬い動詞を使わない
- 相手が直さなかったことを、了承の根拠にしない

## 適用外

議事録の逐語起こし、法務文書・契約書（定型表現が要件）、英語文書、コードのコメント。
