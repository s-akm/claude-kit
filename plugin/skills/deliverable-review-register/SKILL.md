# 成果物レビューと指摘台帳

資料を読んで気づいたことを並べるのはレビューではない。**議事録側と資料側の両方から機械的に抽出し、双方向で照合する。** 人が読んで気づいた分だけを書くと、必ず抜ける。

台帳の書式とテンプレートは `references/register-format.md` にある。

要件定義書が対象のときは、`references/requirement-quality-checklist.md` を先に通す。曖昧語、検証できない書き方、正常・異常・境界の不足、決定と未決の混同など、議事録との照合では出てこない種類の抜けを拾う。

---

## 手順

### 1. 対象と突き合わせ元を確定する

台帳の冒頭に、次の4行を書く。ここが曖昧だと、指摘の網羅性を誰も検証できない。

```
作成日    2026年8月31日
対象ファイル  帳票定義.xlsx、機能一覧.xlsx、…（点数まで書く）
突き合わせ元  7月17日から8月31日までの議事録・要約・全文起こしの全件
点検の方法    各ファイルからコメントと未決を示す記述を機械的に全件抽出し、
              議事録側で抽出した決定事項・宿題・未解決事項と双方向で照合した
```

対象ファイルは版とタイムスタンプまで確認する。レビュー中に相手が更新することがあるため、**作成中に反映された更新は別節に分けて書く**（「本書作成中に反映された更新」）。

### 2. 資料側から機械抽出する

読む前に、抽出できるものを全部出す。

```bash
python3 ../requirements-xlsx/scripts/xlsx_open_items.py 対象フォルダ
python3 ../japanese-business-writing/scripts/scan_expressions.py 対象フォルダ
```

拾うもの。

- セルコメント（通常・スレッドの両方）
- 「要確認」「要検討」「（確認中）」「未定」「TBD」「△」を含むセル
- 空欄のまま残っている記入欄（ヒアリングシートなど）
- 疑問形のまま残っている記述

### 3. 議事録側から抽出する

議事録・要約・全文起こしを全件読み、次の3種類に分けて拾う。

| 種類 | 拾い方 |
|---|---|
| 決定事項 | 「〜で決定」「〜とする」「〜で合意」。**日付と会議名を必ず添える** |
| 宿題 | 誰が誰に何を確認するか。期限があれば期限も |
| 未解決事項 | 議論したが決着していないもの |

決定事項は、**発言のニュアンスまで見る。** 「決定と明言された発言が見当たらない」ことも重要な指摘になる。前提として扱われているのに資料にも議事録にも書かれていない事項は、いちばん危ない抜けである。

### 4. 双方向で照合する

片方向では抜ける。次の2方向を必ず両方やる。

- **議事録 → 資料**：決定事項が資料に書かれているか
- **資料 → 議事録**：資料の未決が議事録で決着していないか

### 5. 区分に分ける

指摘は種類ごとに分けると、対応する側が動きやすい。要件定義資料のレビューでは次の4区分が使える。

| 区分 | 内容 |
|---|---|
| Ⅰ | 確定事項が資料に書かれていない |
| Ⅱ | 資料の未決記述が、議事録では決着している |
| Ⅲ | 未決のまま誰も追えていない |
| Ⅳ | 資料間で食い違っている |

見積書のレビューでは、区分ではなく重要度で分ける。

| 重要度 | 内容 |
|---|---|
| S | 提出前に決着させたい |
| A | 明細内で整合していない |
| B | 明細に該当行が見当たらない |
| C | 前提の脆さ |
| D | 対外提出物としての体裁 |

区分ごとの件数を総括に書く（「指摘は全34件、内訳は確定事項の記載漏れ8件、更新漏れ7件、追跡漏れ11件、資料間の食い違い8件」）。件数があると、相手が対応計画を立てられる。

### 6. 1件ずつ、修正案まで書く

指摘だけを並べても相手は動けない。**1件につき次の4つを書く。**

1. **該当箇所** — ファイル名・シート名・セル番地（またはスライド番号）
2. **現在の記載** — 引用する。要約しない
3. **決定の根拠** — 何年何月何日のどの会議で、何が決まったか
4. **修正案** — そのまま貼れる文面で書く

```
### I-1　帳票の一括ダウンロード方式（帳票定義、最重要）

該当 04_○○帳票 C8・C10、00_帳票定義・管理ファイル一覧 F8・J8

C10は現在「To-Beでの踏襲要否と実施主体を確認。踏襲する場合はZIP化処理の開発が
必要（見積り影響）」となっている。

しかし7月21日の連携仕様整理では、これが決定事項として記録されている。実施主体、
経由するサーバ、署名付きURLでファイルを収集する方式まで決まっている。

見積もりに直結する箇所が、決定から1か月以上「要否を確認」のまま残っている。
修正案としては、C10を「現行仕様を踏襲する。実施主体は自社側とし、連携先の
データ取得APIから取得した署名付きURLでファイルを収集してZIP化する
（2026/7/21 連携仕様整理にて決定）」とし、C8とF8の追加開発に関する一文は
削除するのが妥当である。
```

**見積もりの金額が動く指摘には、そう書く。** 相手の優先順位が変わる。

### 7. 反映済みの事項も記録する

前回の台帳から解消したものを1節にまとめる。相手の作業を認めることになるし、次回の点検で二重に指摘しなくて済む。

### 8. 進め方の案で締める

全件を同じ重みで返すと、相手は着手できない。最後に「どれから片付けるか」を書く。

- 金額が動くもの
- 議事録に決定が残っていて、こちらで修正案まで出せるもの
- 設計フェーズへ送ると後戻りが大きいもの
- どの資料を正とするか決めれば片が付くもの

この4つに仕分けると、たいていの台帳は整理できる。

## 見積書をレビューするときの追加観点

- **対象外とした作業の担い手が書かれているか。** 「対象外」とだけ書かれていると、誰もやらない作業になる
- **グレーアウト行が小計・合計の数式から外れているか**
- **数量と積算根拠欄が一致しているか**（数量は10人日なのに根拠欄が別の前提を指している、など）
- **提示済み資料の数字を下回っていないか**（一度出した下限を後から下げると説明が要る）
- **単価がダミー初期値のまま残っていないか**
- **前提（開発の進め方、責任分界、保守の想定作業時間）が見積書のどこかに書かれているか**

金額への影響は、次の4つに分けて書く。総額をいきなり動かさない。

1. 表示の是正（総額は動かない）
2. 加算を検討したい項目（工数と金額を表で）
3. 建付け次第で加算になる項目
4. 金額を置いていない項目（確認が取れるまで算定しない）

---

## やらないこと

- 読んで気づいた分だけを書く（機械抽出を飛ばさない）
- 指摘だけ書いて修正案を書かない
- 現在の記載を要約して引用する（相手が該当箇所を探せなくなる）
- 決定の根拠に日付と会議名を書かない
- 全件を同じ重みで返す
- 相手が直していない箇所を「了承された」と扱う
- 推測で「決まっていない」と書く（`japanese-business-writing/references/document-structure.md` の申し送り事項の節を参照）

## 適用外

単一ファイルの誤字脱字チェック、コードレビュー、契約書の法務レビュー。
