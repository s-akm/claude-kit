# 基本設計レビューの観点

6 区分。区分ごとに「見つかったもの」と「見たが問題なし」を両方記録する。

---

## A. 要件との整合

| 見るもの | 見つけ方 |
|---|---|
| A-1 設計されていない要件 | 要件 ID の一覧に対して、設計書の対応箇所を埋める。空の行が指摘 |
| A-2 根拠のない設計 | 設計要素の一覧に対して、要件 ID を埋める。空の行が指摘 |
| A-3 反映されていない決定 | `decisions.md` の各行が設計に現れているか |
| A-4 要件と設計の食い違い | 同じ対象について、要件と設計で条件や数値が違わないか |
| A-5 要件の勝手な拡大 | 要件に無い条件や制限が設計で足されていないか |

---

## B. 記述の欠落

| 対象 | 書かれているべきこと |
|---|---|
| B-1 画面 | 画面 ID、名称、遷移、どの権限が使えるか、入力チェック |
| B-2 API・外部連携 | 相手、方式、頻度、タイムアウト、リトライ、失敗したときに誰が気づくか |
| B-3 データ | テーブル、主キー、必須項目、保持期間、削除の扱い、文字数の上限 |
| B-4 権限・ロール | ロールの一覧、できること、できないこと、権限が無いときの画面 |
| B-5 エラー処理 | 想定するエラー、利用者に見せる文言、記録する内容、復旧の手順 |
| B-6 バッチ・定期処理 | 起動時刻、所要時間の見込み、多重起動の扱い、途中で止まったときの再実行 |

**とくに落ちやすい**

- 権限が無いときの画面（エラーにするのか、項目を隠すのか）
- 外部連携が失敗したときに誰がどうやって気づくか
- バッチが途中で止まったときに、頭から流し直してよいか

---

## C. 非機能

区分の記述が 1 つも無い場合は「不要」ではなく「未確認」。不要と判断したなら、その判断を決定事項に残す。

| 区分 | 書かれているべきこと |
|---|---|
| C-1 性能 | 対象の操作、目標値、測定条件（件数、回線、同時利用者数） |
| C-2 可用性 | 稼働時間帯、目標稼働率、計画停止の扱い |
| C-3 セキュリティ | 認証方式、通信の暗号化、アクセス制限、ログの保全、脆弱性への対応 |
| C-4 監視 | 何を見るか、しきい値、通知先、通知の手段 |
| C-5 バックアップ | 対象、頻度、保持世代、復元の手順、復元にかかる時間 |
| C-6 移行 | 対象データ、件数、変換規則、移行できないデータの扱い、切り戻し |

---

## D. 運用・保守・障害対応

| 見るもの | 内容 |
|---|---|
| D-1 運用手順 | 日次・月次で誰が何をするか |
| D-2 保守 | 誰がどこまで直すか。ライブラリの更新をどうするか |
| D-3 障害対応 | 一次切り分けの手順、連絡先、エスカレーションの条件 |
| D-4 引き継ぎ | 運用へ渡す資料の一覧 |

**判定の目安**

障害が起きた夜中に、当番がこの設計書だけを見て一次対応できるか。できないなら不足。

---

## E. 未決の扱い

| 見るもの | 見つけ方 |
|---|---|
| E-1 未決の確定化 | `open-items.md` にある事項が、設計書で断定形で書かれていないか |
| E-2 提案の確定化 | こちらが出した案が、合意の記録なしに確定として書かれていないか |
| E-3 未決の見落とし | 設計上まだ決まっていないのに、どこにも未決として登録されていない点 |

E-3 が一番見つけにくい。B と C を見ながら「これは誰が決めたのか」を毎回問う。

---

## F. 記述の整合

| 見るもの | 見つけ方 |
|---|---|
| F-1 用語 | 同じものを 2 通りに呼んでいないか。用語集と合っているか |
| F-2 識別子 | 画面 ID、テーブル名、API 名が章によって違わないか |
| F-3 数値 | 同じ値が箇所によって違わないか（保持期間、件数、秒数） |
| F-4 図表 | 図の中の名前と本文の名前が一致しているか。図に出てこない要素が本文にないか |
| F-5 版 | 参照している他資料の版が最新か |

**機械で拾える部分**

識別子と数値は、文書から全部抜き出して集計すると食い違いが見える。
用語は `japanese-business-writing` の `scan_expressions.py` と textlint の prh 辞書でも拾える。
