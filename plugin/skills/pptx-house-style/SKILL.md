# PowerPoint 体裁統一（顧客テンプレート追従）

顧客のテンプレートに沿った .pptx を作る／直すときの手順。

**このスキルは「守るべき数値」を持たない。** レイアウトの座標・級数・色は資料ごとに違う。
やることは常に同じ：**既存ページを実測 → その値に新規ページを合わせる → 機械で検証する。**
数値を自分で決めてよいのは、参照できる既存ページが1枚も無い新規デッキのときだけ（その場合は `deck-visual-design` の初期値を使う）。

**方式は2つ。** 顧客テンプレートに追従するときは python-pptx（1〜9章）、テンプレートがなく
デザインを新規に起こすときは HTML で先に組んで pptxgenjs で pptx 化する（10章）。
後者では、ユーザーが持ち込んだ HTML モックが「実測すべき既存ページ」にあたる。

実測結果の書き出し方の例は `references/measured-spec-example.md` にある。

---

## 1. まず実測する（絶対に飛ばさない）

体裁が崩れる原因のほとんどは「既存を見ずに作った」こと。手を動かす前に、
**同じ役割の既存スライドを2〜3枚**選んで座標・級数・色・線幅を吸い出し、表にして自分に見せる。

```bash
python3 scripts/pptx_measure.py deck.pptx --slides 4,6,9
```

出力は次の3つ。

- 各シェイプの `(left, top, width, height)`、フォント名、サイズ、色、`anchor`、`tIns`
- 資料全体の色の出現頻度
- 線幅と線色の組み合わせの出現頻度（12700 EMU = 1pt）

実測したら、**「この資料の規約」として数値を明文に書き出してからユーザーに提示する。**
（例：見出し `left=0.50 / top=1.18 / h=0.28in`、12.5pt 太字 `#0B3B70`）
新規ページはその表に対して1項目ずつ突き合わせる。書式は `references/measured-spec-example.md` に倣う。

## 2. 新規スライドは複製して作る

ゼロから `add_slide()` すると、フォント・余白・自動調整がすべて既定値になり、必ず浮く。
**既存の同種スライドを複製し、中身のテキストと図形だけ差し替える。**
どうしても新規に組む場合は、1で実測した値を1つ残らず明示的に設定する。

## 3. 基本方針

具体値は資料ごとに違うが、方向性は共通。

- 白地・広い余白・**細い横罫線**・抑えた差し色。情報の階層は色数ではなく**文字サイズと余白**で作る。
- 基調はコーポレートカラー1色＋グレー階調。差し色は1枚に1色まで。
- 色ベタ塗りのカードを並べない。装飾ストライプ、意味のない角丸ボックス、影、グラデーションを使わない。
- 全項目が同じ大きさ・同じ色で並ぶ「フラットな一覧」にしない。主役が一番大きいこと。
- **日本語資料のフォントは1書体に統一する**（既存デッキが指定している書体に合わせる。指定がなければ游ゴシック）。
- テンプレートのマスター・レイアウト・フッター・ロゴは必ず継承する。自作しない。

### フォント統一は全レイヤーに流す

スライド本文だけ直すとプレースホルダ由来の文字が別フォントで残る。
theme / slideMaster / slideLayout / slide の **latin・ea・cs すべて**を置換する。

```bash
python3 scripts/fix_fonts.py work/ppt --font 游ゴシック
```

XMLを書き出すたびに毎回流す（生成のたびに元フォントが復活するため）。

## 4. 頻出トラブル6つ（これを知らないと必ず踏む）

`scripts/deckkit.py` に、以下を回避する検証済みのヘルパを入れている。

### (a) 同じ top を指定したのに文字の高さが揃わない

原因は**テキスト枠の設定差**。既定余白の枠と `tIns` 指定済みの枠が混在すると、
枠の上端が同じでも文字の描画位置がページごとにズレる。**揃えたい枠すべてに `deckkit.body()` を適用する**（自動調整オフ、`anchor` 指定、内側余白を0に統一）。

### (b) 罫線が太く濁って見える

`add_connector()` / `add_shape()` は既定のスタイル参照（`<p:style>` の `effectRef`）を持ち、**影が乗る**。
線幅を細くしても解決しない。`<p:style>` を持たない生XMLで引く（`deckkit.rule()`）。
太さは既存デッキから実測した値に合わせる（実測できないときの初期値は 0.5pt = 6350 EMU）。
`add_shape()` で高さ0の矩形を使うと、LibreOffice 等がテキスト枠として自動拡張し**枠に化ける**ので使わない。

### (c) 透明だった枠線が突然見えるようになる

python-pptx の `sh.line.color.rgb = ...` は、**線が `noFill` でも solidFill を足してしまう。**
一括で線色を変えるときは、`deckkit.visible_line()` で可視の線だけを対象にする。

### (d) フォントサイズを上げると本文が下の図に潜り込む

級数や行間を上げる前に、**収まりを機械で測る**。目視では漏れる。
`scripts/pptx_audit.py` の推定描画高さで、次の要素の上端・フッター上端を越えていないか確認する。
フッターまでは 0.5in 以上あけるのが目安。

### (e) 表のセルが意図せず折り返す

列幅は、値そのものではなく**値に付く記号まで含めて**見積もる。「変更あり」は入るのに「変更あり ※」で改行する、という事故が起きる。

```
7.5pt の全角文字は 1 文字あたり約 0.104in
「変更あり ※」= 6 文字相当 → 0.63in ＋ セル余白 0.19in ＝ 0.82in が最低幅
実測では 0.70in で改行し、1.05in で収まった
```

区分列・ステータス列のように短い値が入る列ほど、幅を詰めすぎて事故る。**付加記号を使う予定があるなら、最初からその分を確保する。**

### (f) 見出しが折り返す

セクション見出しは枠幅で切れる。13.5pt の全角文字は 1 文字あたり約 0.19in。
`deckkit.fits(text, width_in, pt)` で判定する。
**枠幅を広げるより、見出しの語を削るほうが体裁が保たれる。**

## 5. 目次ページの作り方

番号・項目名・一行説明を横に並べ、行間に細い罫線を引く形が定型。ピッチは実測値に合わせる。

```python
y = 1.60
for i, (title, desc) in enumerate(items, start=1):
    tb(slide, 0.79, y,        0.37, 0.33)   # 番号
    tb(slide, 1.40, y - 0.02, 5.30, 0.36)   # 項目名
    tb(slide, 6.96, y + 0.01, 5.59, 0.36)   # 一行説明
    rule(slide, 0.79, y + 0.37, 11.76)
    y += 0.4547                              # 行ピッチ
```

一行説明は体言止めで短く書く。10項目までなら 1.60 から始めてフッターに当たらない。

## 6. 日本語の体裁ルール

- **丸付き数字（①②③…）は段落先頭に使わない。** `1.` `2.` `3.` に置換する。
  **固有名詞に含まれるものは残す**（例：`Excel帳票出力API②`、`権限・ロール要件定義書⑤`）。
  判定は「**段落の先頭文字が丸付き数字のときだけ**置換」で安全に切り分けられる（`deckkit.fix_circled()`）。
- 角丸（`roundRect`）は原則使わない。直角（`rect`）に統一する。`avLst` の子要素も消す。
  ただし**表紙の装飾など、既存デッキで意図的に角丸にしている要素は残す**。
- 矢印記号（→ ▶ ⇒）を装飾目的で足さない。既存の文言にあるものは消さない。
- 英字の略称は半角。案の記号のみ全角（Ａ案・Ｂ案）。
- 文章表現は `japanese-business-writing` の規則に従う。とくに見出しとリード文は
  `japanese-business-writing/references/document-structure.md` を通す。

## 6-2. 登壇資料の尺とスピーカーノート

**ページ数だけ決めても尺は合わない。** 20分の資料をリハーサルしたら10分で終わった、という指摘は、
1ページで何を話すかが決まっていないことが原因である。ページごとに秒数を割り当てる。

`data.py` に `NOTES[ページ番号] = (目安秒数, 話す内容)` を持たせ、合計が目標時間になるよう配分する。
書くのは読み上げ原稿ではなく、**話す順番と強調点**。どの項目を厚く扱い、どれを読み上げるだけにし、
どこで一拍置くかまで書く。章扉は10秒、数字1枚のページは35秒、5行の表は70秒が目安。

尺が足りないときに足すのは次の5つ。いずれも話す時間が伸び、かつ内容が薄まらない。

1. 冒頭に「本日の結論」（3点、以降を根拠として構成する）
2. 数字ひとつだけの特大ページ
3. 失敗の時系列シナリオ（放置したらどう進むか）
4. 具体的な事例（社名と数値のある公表事案）
5. 持ち帰り用のチェックリスト

### 配布資料ではノートを pptx から外す

配布前提の資料にノートを入れたまま渡すと、話の組み立てや社内向けの言い回しがそのまま相手に渡る。
**生成側の既定を「ノートなし」にし、原稿は別ファイル（Markdown）へ書き出す。**
リハーサル用にノート入りが必要なときだけフラグで切り替える。

```bash
python3 build_pptx.py 資料.pptx            # 配布用（ノートなし）
python3 build_pptx.py リハ用.pptx --notes  # 手元用（ノートあり）
python3 make_script.py 資料.pptx           # 発表原稿.md を書き出す
```

原稿には、ページ番号・見出し・目安秒数・累計時間を入れる。累計があると、
リハーサルで遅れた地点が分かる。

## 7. 既存資料に手を入れるときの原則

- **文言は変更しない。** 指示が「デザインを整えて」なら、テキストは1文字も変えない。
  丸付き数字の置換のように文字が変わる修正は、事前にユーザーへ確認する。
- **画面モック・ワイヤーフレームの配色は勝手に変えない。** 実装イメージを表す情報なので、
  変えてよいか必ず確認する。変えない場合は、その領域の図形を色置換の対象から外す。
- 迷ったら「触らない」を選び、判断が分かれる点は着手前にまとめて質問する。

## 7-1. 主張の裏づけを先に取る

体裁を整える前に、**主張の柱ごとの根拠を揃える。** 数値がないページに図を足しても厚くならない。
AI駆動開発やバイブコーディングを扱う資料なら `vibe-coding-evidence` スキルを開き、
そこから Web 検索で最新版へ差し替える。出典名と年月は数値と同じページに、
URL は出典一覧のページに置く。

## 7-2. 手修正版を受け取ったときの取り込み

相手が pptx を直接開いて直し、**丸括弧で指摘を書き込んで返してくる**ことがある。
（例：「担う者がいない場合に起きること（言い回しに違和感）」「外部調査（どこの？）では」）
目視で拾うと必ず漏れるので、機械で差分を取る。

```bash
python3 - <<'EOS'
from pptx import Presentation
def texts(f):
    return [[sh.text_frame.text.strip() for sh in s.shapes
             if sh.has_text_frame and sh.text_frame.text.strip()]
            for s in Presentation(f).slides]
A, B = texts("相手の修正版.pptx"), texts("こちらの版.pptx")
for i in range(max(len(A), len(B))):
    a, b = (A[i] if i < len(A) else []), (B[i] if i < len(B) else [])
    for x in a:
        if x not in b:
            print("SLIDE", i + 1, "USER>", x.replace("\n", " / "))
    for x in b:
        if x not in a:
            print("SLIDE", i + 1, "MINE<", x.replace("\n", " / "))
EOS
```

出た差分を3種類に分ける。

| 種類 | 扱い |
|---|---|
| 丸括弧つきの指摘 | 質問か修正指示。中身を読んで対応し、括弧は必ず消す |
| 括弧なしの書き換え | 相手の文言を採用する。こちらの表現に戻さない |
| 削除された要素 | 意図的な削除として扱う。復活させる場合は理由を添えて確認する |

**指摘を1件ずつ潰すのではなく、同じ型を全文へ当てる。** 1枚で「〇〇する〇〇」を指摘されたら、
全ページの列見出しを縦読みして同じ形を探す（`japanese-business-writing` の C-13）。
相手は目についたものから直しているだけで、同種の箇所は必ず他にも残っている。

横展開は目視ではなく走査でやる。**受けた指摘を型に言い換え、その型の正規表現で全ページを叩く。**
一度書いた走査は使い回せるので、指摘を受けるたびに行を足していく。

```python
pats = {
    "口語の可能形":   r"(取れ|選べ|組め|引け|絞れ|気づけ|戻せ|落ち)(る|ない|ます|ません)",
    "口語の比喩":     r"(高くつく|手が届|溜ま|潰す|走る|跳ね返|散らか|回す|乗る)",
    "引用元のぼかし": r"(外部調査|ある調査|一般的に|言われている)",
    "評価語":         r"(重要|妥当|適切|有効|効果的)(?!度|さ)",
    "問いの見出し":   r"(か|のか)$",          # 見出しの文字列だけに当てる
    "作業工程の説明": r"(まとめました|抜き出しました|ヒアリング)",
}
```

**指摘の型を取り違えない。** 「この人（この人って？）」は代名詞の指摘ではなく
**主語が読めないという指摘**なので、他のページで主語を省いている箇所すべてが対象になる。
「外部調査（どこの？）」も同様に、出典名を書いていない数値すべてが対象である。

選択肢が分かれる指摘（対比の見出しの言い換え、図をどこまで足すか、新しい欄をどこに置くか）は、
勝手に決めず**選択肢を示して聞く**。指摘の文面に「〜とかそういうニュアンスで」と書かれていたら、
方向は示されているが表現は委ねられている、という意味である。

### ページを削ったときに直す箇所

指摘で1ページ削除すると、次が芋づるで狂う。まとめて直す。

- 目次のページ範囲
- 章扉とページ番号の対応
- 他ページからの参照（「14ページの一つ目」など）
- 発表原稿の秒数と累計


### 版が複数返ってきたとき

依頼者本人の指摘版と、別セッションで客観的に編集された版が同時に来ることがある。
**三者（自分の版・指摘版・客観版）を総当たりで比較する。**

```bash
# 指摘版 vs 自分の版 → 依頼者の直接の指示
# 客観版 vs 指摘版   → 第三者が独自に直した箇所
```

採否の優先順位は次のとおり。

| 出どころ | 扱い |
|---|---|
| 依頼者の直接の指示（丸括弧つき、書き換え、削除） | 必ず従う |
| 客観版の変更 | 変えた意図を読み取り、意図が妥当なら採る |
| 自分の版 | 上の二つと衝突しない範囲で残す |

**客観版の変更をそのまま丸呑みしない。** 変更が資料全体の整合を崩すことがある。
章扉のタイトルだけを直して目次を直していない、参照先のページ番号が変わっている、
以前に依頼者が指示したスタンスを消している、といった形で出る。
意図を汲んだうえで、整合の取れる形に直して採る。

### 章扉・目次・本文の参照は3点セットで直す

章の名前を変えたら、**目次の行と章扉の見出しを同時に直す。** 片方だけだと必ず気づかれる。
ページを差し込んだら、本文中の「◯ページで示した」を全部洗う。

参照は**相対表現を優先する。**「前ページの」「ここまでに見た」はページを足しても壊れない。
ページ番号を書くのは、離れたページを指す場合だけにする。

### 通しの論理レビューを最後に必ず通す

体裁と文言を直したあと、**流れの断層は別の工程で見る。** `deck-logic-review` を使い、
機械の検査（編集メモの残存、相互参照のずれ、主張の重複、目次とページ範囲の不一致、
出典の孤立、結論と締めの不一致）と、目視の観点（前半で予告した論点が後半で回収されているか、
章題と中身が一致しているか）を通す。作った本人には流れの断層が見えない。

## 8. 納品前チェック（実行して結果を報告する）

### どの環境で実行できるか

| 実行元 | スクリプトを動かせるか |
|---|---|
| ターミナル | 動かせる |
| Cowork（プロジェクトフォルダを接続している場合） | 動かせる |
| Claude デスクトップ単体 | **動かせない** |
| Office アドイン（PowerPoint） | **動かせない** |

下の 2 つでは、人が端末で実行した結果（`90_qa/` の Markdown）を読んで判断する。
スクリプトの実行を促す前に、いまどちらの環境にいるかを確かめる。

### 提出前に 1 ファイルだけ見るとき

```bash
just qa-pptx 説明資料.pptx
python3 scripts/pptx_qa.py 資料.pptx --aft 0   # pptxgenjs で組んだ資料（段落後余白なし）
```

`pptx_qa.py` が次を確認し、`90_qa/<日時>/pptx-<名前>.md` と同名の JSON を出す。

1. **文字切れ** — 推定した本文の高さが枠の高さを超えていないこと
2. **フォントの混在** — 本文に 2 種類以上のフォントが無いこと
3. **図形の重なり** — テキスト枠どうしが面積比 15% 以上重なっていないこと
4. **スライド番号** — 欠落と重複が無いこと
5. **タイトルの重複** — 同じ見出しが複数ページに無いこと
6. **出典** — 数値や図表があるページに出典の記載があること（情報として出す。要否は人が判断する）
7. **空のテキスト枠**

終了コードは 0（指摘なし）、1（警告あり）、2（提出できない指摘、または読めない）。

### 修正前後を比べるとき

```bash
python3 scripts/pptx_audit.py after.pptx --before before.pptx
```

こちらは 1 ファイルのチェックではなく、**触っていない箇所が変わっていないこと**を確かめる道具。

1. **文言差分** — 全スライドのテキストを機械比較し、意図した箇所以外に差分ゼロであること
2. **書式の一様性** — 同種の要素の `(left, top, height, サイズ, 色, anchor, tIns)` を集計し、種類が 1 つに収束していること
3. **フォント** — 目的のもの以外が無いこと
4. **残存物** — 想定外の `roundRect`、段落先頭の丸付き数字が無いこと
5. **はみ出し** — 推定描画下端がフッター上端を越えていないこと

一部ページだけ直した場合は、修正前後を同じ解像度で画像化し、触っていない領域の差分がゼロであることをピクセル比較で確認する（`--pixel-diff`）。

### 目視

```bash
just render-slides 説明資料.pdf
```

全ページの画像と、1 枚に並べたコンタクトシートを `90_qa/<日時>/` に作る。

**納品前の最終確認は PowerPoint から書き出した PDF で行う。** 作業中の確認は LibreOffice でよい。
游ゴシックは LibreOffice で Noto に置き換わり、英数字と日本語の混在行が実機より**広く**描画される。
つまり LibreOffice で収まっていれば実機でも収まる（保守側に出る）。逆に、LibreOffice で
はみ出した行を実機で確かめずに詰めると、実機では余りすぎることがある。

**1 行しかない表のページ、リード文だけで中身のないページは、この段階で見つけて統合する。**
分割した表の 2 枚目以降は、リード文を置かずタイトルの (2/3) だけにする。埋めるために書いた一文は読み手に伝わる。

### 機械の検査に通っても残る、目視でしか拾えない体裁の欠陥

`pptx_qa.py` は文字切れ・図形の重なり・フォント混在を見るが、次の 4 つは通してしまう。
**要確認 0 になったあとに、必ずコンタクトシートで一度見る。**

**(1) 上寄りのページ** — 表や項目の行数が少ないページは、下に大きな余白が残って
未完成に見える。**本文の下端が 6.0in より上で終わっているページを機械で洗い出し**、
行の余白（表なら 1 行あたりのパディング、項目リストなら行間）を配って
6.1〜6.5in に収める。文字を足して埋めない。

```python
for i, s in enumerate(prs.slides, 1):
    b = max(sh.top + sh.height for sh in walk(s.shapes)
            if sh.top / 914400 < 6.8) / 914400
    if 6.55 - b > 0.65:
        print(i, round(b, 2), "余白大")
```

表のヘルパには行の余白を外から渡せるようにしておく（`table(..., pad=0.22)`）。
ページごとに `pad` を変えるだけで縦を合わせられる。

**(2) 1〜2 文字だけが次の行に落ちる（泣き別れ）** — 「週次スポットレビュ／ー」
「必要がありま／す」のような折り返し。**列幅を 0.2in 単位で調整するか、文言を数文字削る。**
列見出しの語が割れているものから直す。列幅を変えたら、隣の列から幅を借りて
表全体の幅は変えない。

**(3) 数字が単位から切り離される** — 「555 億／円」のように、金額や割合が行をまたぐ。
日本語フォントは英数字の前後に空きが入るため、推定より 1〜2 字ぶん幅を食う。
**セル内で明示的に改行を入れて、事実の文と数値の文を別の行に置く。** 折り返し位置を
運任せにしない。

```python
("画面まわり",
 "決済画面が改ざんされ、カード情報を窃取される\n"       # 影響
 "2024年のカード不正利用の被害額555億円、うち9割超が…",  # 数値の根拠
 "日本クレジット協会"),
```

**(4) 左右二段組の段の高さが違う** — 項目数が 4 対 5 のように揃わないと、
短いほうの下に空きが残る。項目を無理に足さず、**二段の下に全幅の囲みを 1 つ置いて閉じる。**
その一文はページの結論にあたるものを選ぶ（話し手のノートに書いた一文がたいてい適任）。

- 結論と本文が食い違っていないか

## 9. 作業後の申し送り

一部ページだけ後から追加されると、そこだけ体裁が崩れる事故が起きやすい。
納品時に、**その資料で実測・確定した数値の一覧**（要素ごとの座標・級数・色・線幅）を
短い表にして添えておく。書式は `references/measured-spec-example.md` に倣う。
次に誰かがスライドを足すとき、その表を渡せば同じ体裁で作れる。

### 生成スクリプトも一緒に渡す

スクリプトで組んだデッキは、スクリプトごと納品物に含める。3ファイルに分けると引き継ぎやすい。

| ファイル | 中身 |
|---|---|
| `data.py` | 本文の文言だけ。表の全行、見出し、注記 |
| `deckkit.py` | 体裁のヘルパ。罫線、淡背景、セル書式、フォント統一 |
| `build_pptx.py` | ページの組み立て |

HTML 先行・pptxgenjs 方式（10章）では `data.js` / `kit.js` / `build.js` に `postprocess.py` と
HTML パーツ（`deck/00_head.html` 〜）、画像化した図の PNG を加える。文言の置換を行ったときは、
その置換一覧のスクリプト（`rewrite.py` など）も同梱し、どの語をどう変えたかを残す。

文言と体裁を分けておくと、次の修正依頼が `data.py`（`data.js`）の書き換えだけで済む。
画像を貼っている場合は切り出し済みのファイルも同梱する。元資料からの再抽出は時間がかかる。

### zip にまとめるときは Python の zipfile で作り、ファイル名は ASCII に保つ

`zip` コマンドは、非 ASCII のファイル名を UTF-8 フラグ（汎用フラグ 0x800）なしで格納する。
受け取った側の展開ツールによっては
「Zip file contains path with invalid characters」と表示されて開けない。

```python
import os, zipfile
with zipfile.ZipFile(out, "w", zipfile.ZIP_DEFLATED) as z:
    for root, dirs, files in os.walk(src):
        dirs[:] = [d for d in dirs if d != "__pycache__"]
        for f in files:
            if f == ".DS_Store":
                continue
            full = os.path.join(root, f)
            z.write(full, os.path.relpath(full, src))
```

あわせて、**zip の中のファイル名とフォルダ名は ASCII にする。** 日本語名が必要なのは
受け取った人がそのまま開くファイル（`AIDD_発表原稿.md` など単体で渡すもの）だけで、
zip の中身は英字名にしておくと環境を問わず開ける。作った zip は
`zipfile.ZipFile(out).namelist()` を出力して、非 ASCII が 0 件であることを確かめる。

## 10. HTML 先行・pptxgenjs 方式（テンプレートのない新規デッキ）

顧客テンプレートがなく、デザインを新規に起こすデッキは、**先に HTML で全枚を組み、ブラウザで
収まりを確かめてから、同じ px 座標で pptxgenjs に写す。** python-pptx でテキスト枠を積む方式は
高さの計算が破綻するが、HTML はブラウザが高さを計算するので、先に HTML で確定させれば
pptx 側は「写す」だけになる。実測の対象は、ユーザーが持ち込んだ HTML モック（CSS のトークン）。

### 工程

| # | 工程 | 出力 | 確認 |
|---|---|---|---|
| 1 | 構成設計書（統合元・削る部分・レイアウトの型・尺） | `構成設計書.md` | ユーザーの確認を取ってから組む |
| 2 | HTML パーツを `deck/00_head.html`（CSS・ナビ）〜 `04_part4.html` に分けて書き、`cat` で 1 枚の HTML にする | `資料.html` | `html_overflow_check.js` で 1920×1080 からのはみ出し 0、図と締めの帯の重なり 0 |
| 3 | 文言を `data.js` に分離し、`kit.js` の部品で `build.js` を書く | `out/資料.pptx` | `Kit.report()` の「枠が小さい」件数 0 |
| 4 | `postprocess.py` で theme と全 run の latin・ea・cs を 1 書体に統一 | 同上 | typeface が 1 つ、最小 pt を出力 |
| 5 | LibreOffice で PDF → `pdftoppm` で画像化し、変更した枚を見る | `out/*.png` | 8章「目視」。LibreOffice は広く出るので、収まっていれば実機でも収まる |
| 6 | `pptx_qa.py --aft 0` と、`japanese-business-writing` の走査 | `90_qa/` | 警告 0 まで直す。段落の行間は XML から読むので、pptxgenjs で明示した行間がそのまま使われる |
| 7 | 発表原稿を Markdown に書き出す（ノートは pptx に入れない） | `発表原稿.md` | 見出しの表を data.js と揃える |

```bash
cat deck/00_head.html deck/01_part1.html deck/02_part2.html deck/03_part3.html deck/04_part4.html > 資料.html
node scripts/pptxgenjs/html_overflow_check.js 資料.html --shots out/html
node build.js && python3 scripts/pptxgenjs/postprocess.py out/資料.pptx --font 游ゴシック
soffice --headless --convert-to pdf out/資料.pptx && pdftoppm -r 60 -png out/資料.pdf out/p
python3 scripts/pptx_qa.py out/資料.pptx --aft 0
```

**文言の修正は data.js と HTML パーツの両方に入れる。** 片方だけ直すと、HTML 版と pptx 版が
別の資料になる。置換は `rewrite.py` のようなスクリプトにして残し、同梱する。

### 換算と判断基準

- 版面は 1920×1080 px。`LAYOUT_WIDE`（13.333×7.5in）に対して **1px = 1/144in、px × 0.5 = pt**。
  8pt 未満は 8pt に切り上げる（`kit.js` の `pt()`）。切り上げた分だけ枠が足りなくなるので、
  枠の高さは切り上げ後の級数で計算する（`k.text` の `'auto'`）
- **図中の本文は 19px（9.5pt）以上、脚注は 16px（8pt）。** Web の UI で見慣れた 13〜16px は投影では
  読めない級数にあたる（「級数の下限」の章）。HTML モックがこれより小さいときは、pptx に写す前に
  HTML 側で級数を上げ、収まりを取り直す
- **画像にする図は、HTML でしか組めないものだけ。** 端末のモック（ブラウザ枠＋DevTools）、複雑な
  模式図の 2 枚程度。`html_to_png.js` で 2 倍解像度の PNG にして貼る。それ以外の図・表・カードは
  図形と文字で組む（文字が選択・編集できる状態を保つ）
- 半透明の地（`rgba(110,124,255,.12)` など）は、**base に混色した実色**として `kit.js` のトークンに
  名前を付けて持つ（`brandBg` `dangerBg`）。透明度は枠線と PDF 変換で崩れる。パレット外の色を
  出さない規則（「色はパレットの外に出さない」）は、この混色まで含めてトークンに置くことで満たす
- 横に並べる文字枠（見出し＋副見出し、タグの列）の幅は**文字幅の見積もりから決める**（`k.textW`、
  `k.headline`、`k.tag` の戻り値）。固定幅にすると隣の枠と重なり、`pptx_qa.py` の「図形の重なり」に出る
- 表は出典一覧と Appendix に限る。出典の URL は出典名の下に 11px で 1 行に置き、表示では `https://` を
  省く。100 字を超える URL は 10px にし、列幅は出典列に寄せる（480 / 1100 / 180 の配分）
- 円弧のリング（割合）は `k.ring` を使う。pptxgenjs の ARC は 90° を越える指定で崩れることがあるため、
  90° ずつに分けて重ねる
- ノートは pptx に入れない（6-2章）。原稿は別の Markdown に、目安秒数と累計付きで書く
- **右下に資料名を再掲しない。** 依頼者の指摘で削除した。脚注は全幅（1760px）で **1 行に収める**。
  2 行になると下端に張り付いて見える。`kit.js` の `k.footer` は右の資料名がないとき自動で全幅にする。
  出典が長い枚は、調査名を略す（「IPA「10 大脅威 2026」」）か、複数の出典を「・」で束ねる
- 級数を 19px に上げて収まらない枚は、項目を削らずに割る。割った後は **ページ番号の対応表**（旧→新）を
  1 つ作り、data.js・HTML・発表原稿の参照（`P\d\d`）を同じ表で振り直す。行番号つきの参照（`P06 20·21`）は
  分割先に合わせて個別に直す。発表原稿は分割した枚に秒数を足し、他の枚から削って合計を戻す

### トークン（Dark／Modern Tech と Light）

`kit.js` に `DARK` と `LIGHT` を持つ。役割名は同じで、値だけ差し替える。

| 役割 | Dark | Light | 使いどころ |
|---|---|---|---|
| base | 0A0A0B | FFFFFF | ページの地 |
| surface / elev | 141417 / 1C1C21 | F7F7F8 / EDEDF0 | パネル / 表のヘッダーと帯の溝 |
| border / borderS | 2A2A31 / 3F3F49 | E1E1E6 / C9C9D1 | 罫線 / 強い罫線 |
| fg / fg2 / fg3 | F4F4F5 / A1A1AA / 63636B | 18181B / 52525B / 8A8A94 | 本文 / 説明 / ラベル・脚注 |
| brand | 6E7CFF | 4F5BD5 | コードの内側・AI 側・先に投じる・記録あり |
| danger | FF4D5E | D93648 | コードの外側・人の判断・後から出る・記録なし |
| ok / warn | 22C55E / F5A524 | 15803D / B7791F | 「画面上は正常」側のみ / 注意 |
| brandBg 〜 warnLine | 混色（kit.js 参照） | 混色 | タグとバッジの地と枠線 |
| termKey / chapterNum | 8FA3FF / 3A3A40 | 4F5BD5 / DCDCE2 | 表紙の端末画面のキー名 / 章扉の特大番号 |
| minusPanel / plusPanel | 181214 / 131420 | FDF5F6 / F3F4FC | 差分表示の「要望のまま」側 / 「受け入れ条件」側の地 |

- **build.js に色の直書きを残さない。** 1 か所でも残すとライト版で黒い箱が出る。`grep -n "'[0-9A-F]\{6\}'" build.js` が
  0 行になるまで役割名をトークンに足す（上の 4 つはそれで増えた）
- **danger は 1 枚に 1 系統。** ok は「画面上は正常に見える」側にだけ使い、良し悪しの評価には使わない
- 版面: 上 64 / 左右 80 / 下 28。h1 54px（y 104）、締めの一文 26px（y 972、全ページ同じ）、
  フッター罫線 y 1024、章扉は枠外
- 表紙・章扉で使う特大の数字は 96〜220px。数字と単位は別 run にして、単位を 24px に落とす
- deck-visual-design の「2色構成」と並ぶ型として使う。白地の顧客テンプレートに Dark を持ち込まない

#### ライト版の作り方（同じ内容・同じ枚数で色だけ差し替える）

pptx は `node build.js --light`（`kit.js` の `T` が `LIGHT` になる。出力名は `…_Light案.pptx`）。
HTML は Dark 版の結合済み HTML から `scripts/pptxgenjs/make_light_html.py 元.html 先.html` で作る。
`:root` の変数・SVG の直書き色・`rgba()` の色味を DARK→LIGHT の対応表で置換し、残った hex が LIGHT の値だけに
なったことを出力で確かめる。P04 の端末モックのような画像は、ライト版の HTML から撮り直す
（`shotimg.js` の URL と出力名を差し替える。**セクションの `data-n` は分割・採番で変わる**ので、撮る前に対象の番号を確かめる）。
QA は Dark と同じ連鎖を通す。ライト版で追加で見るのは、白地で薄すぎるタグの枠線（`*Line` の値）と、
`rgba` の濃度（Dark の .35 は白地では .28 程度に落とす）。

### 今回踏んだトラブルと回避策

| 事象 | 原因 | 回避策 |
|---|---|---|
| 出典表の長い URL が次の行に重なる | 1 行に収まらない URL を固定行高の表に置いた | 列幅を出典列に寄せ、`https://` を省き、100 字超は 10px。それでも収まらなければ行高を上げる（`rh`） |
| タグの幅が日本語で足りない | ASCII と同じ幅で見積もった | 文字幅は ASCII 0.55em・それ以外 1em で見積もる（`textW`）。ASCII 8.5px / CJK 15px＋左右 15px |
| 見出しの横の副見出しが見出しの枠に重なる | 見出しの枠を固定幅 420px にした | 見出しの枠幅を文字幅から決め、副見出しの x をその右に置く（`k.headline`） |
| 単一行の枠が `pptx_qa.py` で「文字切れ」に出る | 枠の高さを元の px で決めたが、8pt 切り上げで級数が上がった | 枠の高さは切り上げ後の級数×行間で取る（`'auto'`）。`Kit.report()` を 0 にしてから納品 |
| `pptx_qa.py` の「空のテキスト枠」が数百件 | pptxgenjs の図形は txBody を持つため、パネルが文字枠に数えられた | 塗りか枠線のある図形は文字枠に数えない（修正済み） |
| 特大の数字＋単位の枠が「文字切れ」に出る | 推定が段落の最大級数で全文字を数えていた | run ごとの級数で幅を数える（修正済み） |
| 表紙だけ `display:flex` が効かない | `.slide.active{display:block}` が後勝ち | `.slide.cover.active{display:flex}` を足す |
| 出典の数値の向きを取り違えた | 「基準を満たした割合」を「満たさなかった割合」の列名で置き、赤の強調が逆になった | 出典の数値が **合格率か不合格率か** を列名と強調色の両方で照合する。締めの一文と向きが合わないときは列名を疑う |
| 表紙に根拠のない数値（critical: 6）を置いた | 雰囲気のために作った | モック値でも、意味を持つ数値は置かない。状態語（open / ui: all green）にとどめる |
| HTML 版と pptx 版で文言が 3 か所ずれた | 片方だけ直した | `japanese-business-writing/scripts/check_html_data.js data.js deck/*.html` で data.js の文字列が HTML にあるかを突き合わせる（H-12） |
| ライト版で章扉の番号と差分パネルが黒いまま | build.js に色を直書きしていた | 直書きを 0 にし、役割名でトークンに置く（termKey / chapterNum / minusPanel / plusPanel） |
| ライト版の画像が別のページの図になった | `data-n` が分割・採番で 09 → 10 にずれていた | 撮る前に `grep 'data-n="10"'` で対象を確かめる |

| ページ番号 | 11.8 |

**図中の本文は8社が12.0〜13.3ptという狭い帯に収まる。** ページごとの最小級数の中央値も12.0〜14.2pt。
詰まったページ（下位10%）でも8.0〜11.8pt。**8ptを割るのは脚注と軸の単位注記だけ。**

→ **投影して読める下限は11pt。** 図の中に8.5ptを置くのは、実企業では脚注の級数を本文に使うことになる。
図が入りきらないなら級数を下げるのではなく、ページを割る。

### 1ページの論点

母数120ページで、1論点が70%、2論点が14%、3論点以上が16%。
**3論点以上だったページは全部が「サマリー・全体像・一覧・3つの理由」型で、説明のページには1枚もない。**

本文ページの文字数は中央値399字、上位25%が563字、上位10%が758字。1,000字超は3.3%で全部が表かリスク一覧。

### 資料全体の分割

- 章あたり5〜15ページ（中央値9）
- 章扉は本編の13〜18%。10社全部が章扉を持つ
- 冒頭サマリーは10社中6社
- Appendix は10社中7社（sansan は51%がAppendix、UNITED ARROWS は0）
- 目次は全社1枚。arent と sansan は章扉で再掲

## 同じ主題を複数ページに割るとき（実企業IR資料107ページ・54組の実測）

8社のIR資料から、隣り合う2〜3ページが同じ主題を扱っている組を54組拾い、
どこで切っているか・見出しをどう書き分けているか・何を再掲しているかを数えた。

### 切り方の型（54組）

| 型 | 件数 |
|---|---|
| 総論→各論 | 16 |
| 対象別に分割（顧客・事業・地域・領域・機能） | 14 |
| 属性別に分割（何をするか／誰がやるか／いくらかかるか） | 7 |
| 全体→内訳 | 3 |
| 現状→打ち手 | 3 |
| 一覧→深掘り | 3 |
| 時系列で分割 | 2 |
| 主張→他社事例で裏づけ | 2 |
| 打ち手→効果の裏づけ | 2 |
| 総括→数値 | 1 |
| 一覧の分冊 | 1 |
| 事実→解釈 | **0** |

**「情報が多すぎる」と言われたときは、まず論点の数ではなく属性の数を数える。**
1つの論点に貼った属性が5つ以上なら、属性別に割る。
実測のカード型ページは、帯＋見出し＋説明＋タグの**4属性まで**で止め、
それ以上（詳細・料金・体制）は必ず次ページの表に送っていた。

### 連番の付け方（54組）

| 付け方 | 件数 |
|---|---|
| 連番なし（主題語を据え置き、後半だけ差し替える） | **36** |
| 丸数字 ①②③（内容の番号として） | 9 |
| 階層連番 1. / 1-1. | 6 |
| .01 / .02 | 2 |
| 括弧書きで区別（通期／四半期） | 1 |

**「(1/2)」「その1」のような “何枚中の何枚目” を明示する書き方は107ページ中0件。**
標準は「主題　- サブタイトル」の形で、ハイフンの後だけ差し替える。

### 再掲（54組）

| 再掲の仕方 | 件数 |
|---|---|
| 1ページ目の要素名だけを再掲（カード名を見出しに昇格、バッジ・黒帯で現在地表示） | 32 |
| 枠組み（表や図の型）をそのまま再掲して中身を差し替え | 12 |
| ページまるごと再掲 | 3 |
| 再掲なし | 7 |

**再掲ありが87%。**2枚目に何も引き継がない切り方は少数。よく使われる手は4つ。

1. 1枚目のカードの帯に書いた言葉を、2枚目の主見出しにそのまま持ってくる
2. 総論図を右上に縮小して再掲し、当該部分だけ濃くする
3. 属性表の枠だけを再掲して中身を入れ替える
4. パンくず・黒帯・丸バッジで現在地を示す

再掲であることを見出しに明記していたのは**「【再掲】」1件のみ**。
同じページを別の章でもう一度使うときだけ付ける。

### 締めの一文をどちらに置くか

結論は各論の後ろ、つまり**最後のページの末尾**に置く。
1枚目の末尾に置くのは、その図から読み取れる観察（体言止め）までにとどめる。

## 版面を先に決めて、図に高さを計算させる

ページごとに図の置き方を決めると、ページをめくったときに結論の位置が動く。
**締めの帯の高さを固定し、図はその上で上下中央に置く。**

```
1.90  図の領域 上端（FIG_LO）
6.16  図の領域 下端（FIG_HI）
6.26  締めの帯（BAND_Y）。高さ0.46。全ページ同じ
6.88  脚注
7.10  細い罫線 ／ 7.18 資料名とページ番号
```

**図の関数に `top` を渡さない。** 各関数が自分の高さを計算し、
`FIG_LO + (FIG_HI - FIG_LO - 高さ) / 2` に置く。これで、内容の少ないページでも
図が版面の中央に来て、下だけが空く不格好が出ない。

1ページに2ブロック積むときだけ、上のブロックに `top=FIG_LO` を渡して上詰めにし、
下のブロックには前のブロックの戻り値を渡す。

## ページ番号は採番させる

章ごとにページ番号を手で書くと、1ページ挿すだけで全部ずれる。
**共通の外枠モジュールに採番器を持たせ、ページを閉じるたびに1つ進める。**
巻末だけ別系列（A-1、A-2…）にする。

相互参照の文面に「29ページで挙げた要望」と書かない。
番号は動く。「本編の要件定義のページで挙げた要望」と、章か主題で指す。

## 納品前の機械検査（6項目）

**指摘が0件になるまで直す。** そのうえでPDFに変換し、画像にして目で見る。

| # | 見るもの | 判定 |
|---|---|---|
| 1 | 文字が枠に収まっているか | 必要な高さ > 枠の高さ なら指摘 |
| 2 | 図形が版面の外に出ていないか | x<0 / x+w>幅 / y<0 / y+h>高さ |
| 3 | 塗りのある図形どうしの重なり | 小さいほうの面積の18%超で指摘。意図的な重ねは名前に接頭辞を付けて除外 |
| 4 | **図が締めの帯に掛かっていないか** | 図形の下端 > BAND_Y なら指摘 |
| 5 | **表のセルが行の高さからはみ出していないか** | 表を組む関数の中で停止させる |
| 6 | **脚注がフッターの罫線に掛かっていないか** | 脚注の上端＋必要な高さ > 罫線の位置 なら停止 |

4〜6は、1〜3だけでは拾えない。**1〜3が0件でも版面は崩れる。**

**運用の下限は 9.5pt。** 図の領域（版面の1.86〜6.30in）に 9.5pt 未満を置いたら機械で止める。

## 色はパレットの外に出さない
